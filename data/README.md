# Data & Feature Engineering Module

Owner: Mohit. This module turns raw Kaggle "Home Credit Default Risk" data into
`data/processed/features.csv`, the frozen input table the model-training module
(Mithunn) trains on. It does not train a model, serve an API, or render UI.

## Pipeline

```
data/raw/application_train.csv  ─┐
data/raw/bureau.csv              ├─► feature_engineering.py ─► data/processed/features.csv
data/processed/synthetic_transactions.csv (from synthetic_transactions.py) ─┘
```

`application_train.csv` and `bureau.csv` are the raw Kaggle files and are not
regenerated by anything here. `synthetic_transactions.py` simulates daily
UPI-style cash flow per applicant (there is no real bank transaction data
available), and `feature_engineering.py` combines all three sources into the
final feature table.

## How to regenerate `features.csv` from scratch

```bash
cd data
pip install -r requirements.txt
python synthetic_transactions.py   # writes processed/synthetic_transactions.csv (~55M rows, ~1.8GB)
python feature_engineering.py      # writes processed/features.csv
```

Both scripts are deterministic (`numpy.random.default_rng(42)` in
`synthetic_transactions.py`) — rerunning produces byte-identical output.

Note: `data/raw/*.csv` and `data/processed/*.csv` are git-ignored. They are
regenerated locally rather than committed, because the raw Kaggle files
(166MB, 170MB) and the synthetic transactions file (~1.8GB) exceed GitHub's
100MB per-file push limit. Only the scripts, this README, and
`requirements.txt` are committed.

## Features in `features.csv`

**`applicant_id`** — Direct copy of `SK_ID_CURR` from `application_train.csv`.
The unique identifier joining this table back to the raw applicant record.

**`income_ratio`** — How large an applicant's income is relative to the loan
amount they're asking for. Computed as `AMT_INCOME_TOTAL / AMT_CREDIT`. A
higher ratio means the applicant earns more relative to what they owe, which
is generally a good sign. Where `AMT_CREDIT` is 0 (a data artifact, not a
real loan), the ratio is treated as missing and imputed with the dataset
median rather than producing a divide-by-zero.

**`cash_flow_stability`** — How consistent an applicant's daily income is,
based on the 180-day simulated transaction history. Computed as
`1 / (1 + std(daily_inflow) / mean(daily_inflow))` over the window, so it
sits in roughly [0, 1]: close to 1 means very steady daily inflow, closer to
0 means highly erratic income. Applicants with zero mean inflow get a score
of 0 rather than an undefined ratio.

**`revenue_trend_slope`** — Whether an applicant's income is trending up or
down over the 180-day window. Computed as the slope of an ordinary
least-squares line fit to `daily_inflow` against the day index (0–179). A
positive slope means income is growing; negative means it's shrinking
(this is the signal the synthetic "declining" applicants are designed to
produce).

**`bill_punctuality`** — A proxy for how reliably an applicant pays existing
obligations on time. **Approximation:** the raw dataset has no literal bill/
utility payment history, so this is derived from `bureau.csv`'s
`CREDIT_DAY_OVERDUE` field (days a bureau-reported credit line is currently
overdue), averaged across all of an applicant's bureau records, then
transformed to a bounded score: `1 / (1 + mean_overdue_days / 30)`. Zero
overdue days across all records gives a score of 1.0 (perfectly punctual);
more/longer overdue periods push the score toward 0. Applicants with no
bureau records get the dataset median.

**`gst_regularity`** — A proxy for how consistently an applicant's business
reports/files (standing in for GST filing regularity, which isn't in this
dataset). **Approximation:** derived from how evenly spaced an applicant's
bureau credit-update records are over time. For each applicant, we take the
gaps between consecutive `DAYS_CREDIT_UPDATE` values (sorted) and compute
their standard deviation, then transform: `1 / (1 + std(gaps) / 180)`. Small,
even gaps (regular reporting) produce a score near 1; large, irregular gaps
produce a score near 0. Applicants with 0 or 1 bureau record (no gap to
measure) get the dataset median.

**`ext_source_avg`** — Mean of `EXT_SOURCE_1`, `EXT_SOURCE_2`, `EXT_SOURCE_3`
(three anonymized external credit-bureau-style scores already in the raw
data), ignoring whichever of the three are null for a given applicant. If
all three are null, the dataset median is used.

**`employment_stability`** — Years of continuous employment/business tenure,
derived from `DAYS_EMPLOYED` (`-DAYS_EMPLOYED / 365`, clipped to [0, 50]).
**Cleaning note:** the raw dataset uses `365243` as a placeholder value in
`DAYS_EMPLOYED` for applicants where the field doesn't meaningfully apply
(a known Kaggle data quirk); this is treated as missing and imputed with the
dataset median before computing years employed.

**`target`** — Direct copy of `TARGET` from `application_train.csv`.
`0` = repaid, `1` = defaulted. This is the label the model will be trained
against.

## Data cleaning summary

- `DAYS_EMPLOYED == 365243` → treated as missing, median-imputed.
- Any per-applicant feature that ends up null after computation (e.g. no
  bureau records, all `EXT_SOURCE_*` null) is median-imputed — no rows are
  ever dropped, so `features.csv` always has exactly one row per applicant
  in `application_train.csv`.
- `income_ratio` divide-by-zero (`AMT_CREDIT == 0`) → treated as missing,
  median-imputed.
- `cash_flow_stability`, `bill_punctuality`, and `gst_regularity` are all
  clipped to `[0, 1]` after imputation.
- The final table is asserted (in `feature_engineering.py`) to contain no
  NaN or infinite values before it's written.

## Schema of `features.csv`

| Column | Type | Range |
|---|---|---|
| `applicant_id` | int | unique, matches `SK_ID_CURR` in `application_train.csv` |
| `income_ratio` | float | ≥ 0, unbounded above (typically 0–20) |
| `cash_flow_stability` | float | [0, 1] |
| `revenue_trend_slope` | float | unbounded, ~[-1000, 1000] in practice (currency units/day) |
| `bill_punctuality` | float | [0, 1] |
| `gst_regularity` | float | [0, 1] |
| `ext_source_avg` | float | typically [0, 1] (source scores are pre-normalized in the raw data) |
| `employment_stability` | float | [0, 50] (years) |
| `target` | int | {0, 1} |

Row count: one row per applicant in `application_train.csv` (307,511 rows).

## Synthetic transaction generation (`synthetic_transactions.py`)

Since no real bank transaction data is available, daily inflow/outflow per
applicant is simulated from `AMT_INCOME_TOTAL` over a fixed 180-day window
(2025-01-01 onward). Per applicant:

- Base daily inflow = `AMT_INCOME_TOTAL / 365` (floor of 50 to avoid
  degenerate all-zero series for zero/near-zero income applicants).
- ~50% of applicants get a "weekend dip" (0.5–0.8× multiplier on
  Sat/Sun), standing in for business types with lower weekend activity.
- Each applicant is randomly assigned one of three trend/volatility
  profiles: **normal** (85%, roughly flat to slightly growing, low noise),
  **declining** (8%, inflow trends down to 35–65% of its starting level by
  day 180 — the intended risk signal), and **volatile** (7%, no strong
  trend but 2–3x the noise of a normal applicant).
- Daily noise is multiplicative Gaussian on top of the trend/seasonality.
- Occasional spikes (2–5% of days) simulate bulk payments (inflow, 2–5x
  multiplier) or restocking/bulk purchases (outflow, 1.5–3x multiplier).
- Outflow is generated independently from inflow, using a per-applicant
  baseline ratio (55–95% of inflow) plus its own noise and spikes.
- All values are clipped to ≥ 0.
- Random seed is fixed (`numpy.random.default_rng(42)`), so the output is
  reproducible across the team.

This file is an intermediate artifact only — it exists to make
`cash_flow_stability` and `revenue_trend_slope` computable, and is not part
of the frozen feature contract itself.
